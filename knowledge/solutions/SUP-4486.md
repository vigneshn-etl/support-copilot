## Knowledge gained (techno-functional — required)

**Technical:** pivotdefn .ftl includes can be shared across many pivotdefns; a single commented-out HAVING clause in a shared include silently changes row counts for every consumer. Bulk 'sync from configuration bucket' commits can regress config that was previously correct and aren't guaranteed additive — diff them. Sibling include files with near-identical names (history_product_ty_ly_lly.ftl vs _style_ty_ly_lly / _sku_ty_ly_lly) can diverge in correctness even when they look like copy-paste variants — check all siblings, don't assume uniformity. View→pivotdefn mapping lives in uidefn/conf/AssortmentUiConf.confdefn (view id -> model) plus uidefn/model/<Model>.modeldefn (model -> pivotDefn); two views with the same-looking name/section can point at completely different pivotdefns and thus different include chains. OCI live-config buckets layer configuration/ (base, synced from a bucket path that git also syncs FROM) + override_configuration/ (manual per-env hotfixes) + a git_hash marker recording provenance.

**Functional:** Stylecolor Review's Collection View and Top TY vs LY are expected to show the same product/stylecolor population for a given scope — they are cross-checked by users specifically because they should reconcile. FLOW_TABLE_SELECTION_CRITERIA / HIST_TABLE_SELECTION_CRITERIA encode the business rule for which stylecolors count as 'in scope' (e.g., receipt-flow based selection); dropping that filter over-counts product that shouldn't be in the TY/LY/LLY comparison.
