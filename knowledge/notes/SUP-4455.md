## Problem

Belk Prod users published 4 DP-828 stylecolors from PO Publish View on
2026-07-29 (~10:25 AM EDT). The UI showed publish timestamp/user, but the
ClickHouse outbound archive had no rows for them and Belk received nothing.
All 4 rows showed `Publishable Status = FALSE`. Priority Highest, prod.

## Diagnosis path

- **Wrong first read (our own, comment 58636):** the reporter's check query
  filtered `plan_name` with stylecolor UUIDs; `plan_name` holds the readable
  plan name ("D828 MELA PAINTERLY BLOOMS"), so it could never match. Filtering
  on `S5_STYLECOLOR_ID` returned rows (1040 across the 4 ids), each with
  `MESSAGE_ID_FROM_PUBSUB`. We told the customer "not a data-loss issue".
  **This was premature** - Nicole Rockwell (08-06) pointed to a Slack thread
  where Chris McGinley said nothing had gone out after the first publish.
- Traced the pipeline from the ETL repo/lineage: Postgres `blk_p_pinchpo`
  (`is_published`, `published_at`) -> `pinchpo_sync.sh` (every minute) ->
  ClickHouse `from_pg_blk_p_pinchpo` -> cyclic `po_create.sh` (every 15 min,
  ~11:00-05:00 EDT, Mon-Sat) -> `sync_outbound_published_memory` (gate:
  `is_published=1` AND `published_at + 4h` inside the run's sync window) ->
  `sync_outbound_order_flow_memory` -> `..._archive_tbl` -> pub/sub.
- Suspects ruled out with live data (observed): clone-flag theory from SUP-4034
  (`blk_p_pinchpo.is_published=1`, `blk_p_dc_adj.dc_publish=1` for all 4).
  Cron-gap (05:00-11:00 EDT) and unlocked-cron-race (BD lock-race note) were
  floated; the +4h window (18:10 UTC) fell inside cyclic hours, so both looked
  unlikely (inferred - the delta-window/log checks were requested, results not
  recorded in session).
- Observed timing: UI "Last Published Timestamp" = `blk_p_dc_adj.published_at`
  (UTC stored, shown in New York time). The archive rows we saw were created
  by a later cyclic run, after Chris edited `published_at` by hand. The
  "10:30 AM vs 6:15 PM" confusion was UTC vs EDT display of the same row.
- **Root cause (per Chris, JIRA comment 08-12 and Slack):** the initial publish
  failed because the items had no valid sizes
  (`blk_p_poattributedefaults_tbl.default_validsizes_store/ecom = []`). The old
  PO Publish View let the user publish anyway; the UI stamped the publish
  fields but outbound generation had no valid size to build a row from, so
  nothing was archived/sent. Users then picked sizes, and Chris's manual
  `published_at` nudge made the next cyclic run send them. SUP-4372 ("Prevent
  PO Publish When No Valid Sizes Are Selected") prevents it once deployed.
- Not proven: the table was only checked after the fact (no history), and Belk
  claimed sizes were selected at publish time. Chris's own wording is
  "theory"; the ticket was closed without a stronger audit trail.

## Fix

No code change on this ticket. Data was remediated manually by Chris
(`published_at` update, picked up by the next cyclic run). Prevention lives
in SUP-4372. Closed 2026-08-30 with "reopen if it recurs".

## Verification

Archive rows for the 4 stylecolors exist with pub/sub message ids (our query,
comment 58636; PROD extract attached to the ticket). Note this verifies the
later manual resync, not the original publish.

## Knowledge gained (techno-functional - required)

**Technical:** `sync_outbound_order_flow_memory_archive_tbl` is written only by
the cyclic batch, one row per store location per published plan (a 92-store
example produced 92 rows with one timestamp). Key by `S5_STYLECOLOR_ID`, not
`plan_name`. A row appears at roughly `published_at + 4h` on the next 15-min
cyclic tick (we matched this on a 2025-09-10 publish). Re-clicking Publish on
an already-published row only refreshes `updated_at/updated_by` in
`blk_p_pinchpo` (upsert does not rewrite `published_at`) and queues a replan.
The PO Publish View grid applies gates in order: channel scope
(`blk_ma_stylecolorchannelattributes`, `record_state=0`) -> a PO row in
`blk_p_purchaseorders_tbl` for the selected weeks -> publishable eligibility
-> `blk_p_flowsheet.dc_validwk`.

**Functional:** "Publishable Status = FALSE" next to a populated publish stamp
meant "already published", not "failed". A UI publish stamp is not proof that
Belk was sent anything; the proof is the archive row plus pub/sub id. Valid
sizes (`blk_ma_sizeattributes`: `source_member_id` not null/'NONE',
`sku_status=0`) are a prerequisite for the outbound PO feed.

## Gotchas

- Cyclic temp tables are truncated every batch run, so a missed publish is
  hard to investigate days later - ask support to report impacted items
  immediately (Chris, 08-11).
- ClickHouse sessions display timestamps in different time zones for different
  people; convert before comparing against Slack/UI times.
- Do not post "not a bug" before checking engineering's Slack thread/status.
