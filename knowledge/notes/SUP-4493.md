## Problem

The EXP (Express) prod weekly batch of 2026-08-09 aborted in the bulk-plan stage
("Too many items failed, aborting", 16,932 > the 1,000 threshold). Every plan task failed
with the same ClickHouse error. Ticket asked to find why `store_master_new_tbl` had
duplicate rows (hint from Chris McGinley on 2026-08-11: look at
`bash/weekly/update_weekly_ch.sh` ~L355).

## Diagnosis path

Evidence in the order it was gathered:

- ETL log (`weekly.sh` trace) only shows the poll loop in `batch_plan.py`
  (`get_current_status()` hits `.../plan/queueStatus` every 60 s) and
  `ERROR:root:Too many items failed, aborting`. That line is a threshold check, not a
  diagnosis; the batch script is a bystander.
- The real error came from darwin's `planner.log` (`AsstPlanTask`, "assortment plan task
  failed, setting all items to failed"): ClickHouse `Code: 190 ... Arrays passed to arrayMap
  must have equal size: arrayMap(lambda, uncBOH :: 10, prevEOH : 19)`. Traced through
  `PivotDispatcher.runSQLStatement` to `EXP01_FlowSheetPlanPivot.pivotdefn`
  (`arrayMap((a,b) -> (a - b), uncBOH, prevEOH)`, lines ~3549/3579/3609 on express-configs
  `main`; the live prod branch was not confirmed). `uncBOH` is a `groupArray(...)` per
  week; `prevEOH` is the previous iteration's array via a session temp table.
- Inferred, then confirmed by the CH query below: not a darwin/config bug; the arrays differ in length because the store-level rows
  feeding `groupArray` are duplicated for some weeks.
- Owner queried CH: `store_master_new_tbl_pre` had duplicate
  `(product, channel, location, time)` keys between `2027_W40` and `2028_W13`;
  `exp01_PlanMeta.planEnd = 2027_W40`. Clearing the dups and re-running the batch from the
  bulk-plan step succeeded (the one-off recovery).
- **Root cause:** `update_weekly_ch.sh` rebuilds `store_master_new_tbl_pre` every week, then
  runs a hardcoded "projection" block (added by SUP-3890 on 2026-03-30 to extend the table
  10 years) that clones rows into future weeks from fixed literals (`# Balance of 2027`
  starts at `2027_W40`, year blocks `2028`-`2036`, manual `2028_W53`/`2034_W53`). In March the
  real data ended at `2027_W13`, so no overlap. The real extract's horizon advances weekly
  and by August reached `2028_W13`, so real rows and synthetic clones both exist for
  `2027_W40`-`2028_W13`. The window widens every week, so it would recur.
- Reproduced on a test table: `test_store_master_new_pre` copied from
  `store_master_new_tbl_backup` (37.86M rows, 0 dups), replayed the buggy
  `# Balance of 2027` insert -> 1,180,296 duplicate groups (= 90,792 combos/week x 13 weeks).

## Fix

- Two options were designed. A fully dynamic projection (start from MAX(time) of real data
  up to `exp01_time` max, replacing the hardcoded literals) was drafted but the team chose
  to keep the current logic and only prevent duplicates. Backup alternative: add
  `and (product,channel,location,insert_time) not in (select ... from store_master_new_tbl_pre)`
  to ~12 year-block inserts (documented in `tickets/SUP-4493/backup-fix-NOT_IN-alternative.md`;
  not chosen).
- **Chosen:** dedup at the final load, `bash/weekly/update_weekly_ch.sh`
  (branch `SUP-4493` off `etl_assortment_planning_upgrade`, commit `bbd77cb`): replaced
  `insert into store_master_new_tbl select * from store_master_new_tbl_pre` with a
  `GROUP BY product, channel, location, time` select using `any()` for the other columns
  (aps_index, grade, bi, strclimate, strmenscapacity, strwomenscapacity, indx, eventdate).
- PR: s5-stratos/etl-exp-batch#233 (JIRA comment 2026-08-13); deployed to prod, ran clean
  (Jatin Rana, 2026-08-16).

## Knowledge gained (techno-functional — required)

**Technical:** `store_master_new_tbl` is truncated and rebuilt from `_pre` every weekly run,
so a data cleanup only fixes one run; fixes must be in `update_weekly_ch.sh`. ClickHouse
`MergeTree` does not enforce keys, and `groupArray()` over duplicate keys produces
different array lengths for adjacent weeks, which crashes pivots that `arrayMap` two
shifted arrays (the FlowSheetPlan `uncBOH`/`prevEOH` loop). "Too many items failed" in
`batch_plan.py` is only a threshold; the cause is in darwin `planner.log`.

**Functional:** `store_master_new` holds per-store, per-week attributes (APS index, grade,
climate, capacity) that planning reads for the full planning horizon. A bad week of
store rows fails the whole bulk plan, i.e. no refreshed plan for any style on Monday.

## Gotchas

- `any()` picks arbitrarily between a real row and a stale synthetic clone; there is no
  provenance column. If a store's attributes changed year over year, the wrong one could
  be kept silently. Accepted trade-off.
- The hardcoded literals remain: the `2036` ceiling (`exp01_time` reaches `2037_W52`) and
  the manual 53rd-week handling for 2028/2034 are still fragile, and the SUP-3890 block
  still runs unchanged. Worth a follow-up ticket.
- The live prod branch of express-configs was not confirmed (`main` was read); the batch used
  `NOW=20260809050001` America/New_York and planner.log is UTC (error at 11:36:30 UTC, ~2h36m
  after start), so correlate by timezone, there is no shared request id.
- Related: `knowledge/notes/PROD-EE-20260809-new-store-backtest-backfill-missing.md` (a
  different EE batch failure the same day; do not conflate).
