## Problem

Belk: on-order for style 476400837.003 (Dept 365) showed 150 units for W23,
but the PO (3877209) carried 4 SKUs totalling 900 units. Only the XXL SKU
surfaced in the style total. Wider than one style — multiple POs affected.

## Diagnosis path

- Vertica `BLK_IN_ACT_ONORDER`: all 4 SKU rows present with correct units →
  inbound file OK, not an extraction issue.
- PG `blk_ma_sizeattributes`: 4 of 5 sizes mapped to internal UUID products;
  only XXL kept the raw Belk id → **id-mapping mismatch suspected**.
- CH `blk_p_onorder_by_po`: rows carried mixed/wrong SKU ids and duplicated
  units for some sizes.
- **Root cause:** onorder was joined to `ref_s5_client_id_mapping` using the
  *S5 sku id* — which Belk does not send. Also the mapping table contained
  duplicate rows (Belk size-attribute changes created multiple S5 skus per
  Belk sku), double-counting on-order where the join did hit.

## Fix

1. Join onorder → `ref_s5_client_id_mapping` on the **Belk sku id** instead
   of the S5 sku id.
2. De-duplicate `ref_s5_client_id_mapping` before the join so repeated
   S5-sku↔Belk-sku pairs can't multiply units.

(ETL repo, onorder transform — locate via
`python3 lineage/query.py upstream blk_p_onorder_by_po`.)

## Verification

QA pre/post snapshot of department-level OO totals by Stephanie; totals
matched upstream PO after re-run. Moved to Ready for Client Deploy.

## Gotchas

- Client id-mapping tables can silently accumulate duplicates when the
  client changes size attributes — check for dupes *first* whenever a
  quantity metric is inflated or SKUs are missing.
- Clients differ in which id they send (Belk: native sku id, not S5 id).
  Never assume the join key that works for one client works for another.
