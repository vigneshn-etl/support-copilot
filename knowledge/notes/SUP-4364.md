## Problem

EE stylecolor `PIM-465531` (style `PIM-465526`, Lil Rambler Zip Sneak) showed
Regular waist sizes (24-32) and no On Order in Style Edit / Flowsheet, although
the style's size run had been re-coded to `Waist-US-Petite` and 250 units
(9 SKUs, PO 300441) existed upstream. Prod, reported by Stephanie McDaniel.

## Diagnosis path

- Compared the four levels (queries in the ticket): `eve_ma_styleattributes`
  (style) = `Waist-US-Petite`, PIM/ERP source `eve_in_prd_attrsku` = `24P`-`32P`,
  but `eve_ma_stylecolorchannelattributes.ccrangecode` = `Waist-US-24-32 - CL-004`
  with `cc_validsizes_*` = `{}`, and `eve_ma_sizeattributes` still Regular rows.
  So style level was right; channel and SKU levels never re-synced.
- **Why the daily/weekly batch never re-synced:** the batch reloads these PG
  tables with `DELETE` + `\copy`, never an `UPDATE`. The sync trigger only fires
  `AFTER UPDATE OF sty_size_run_name` / `UPDATE OF ccrangecode`, so a bulk reload
  never runs it (read in the trigger/function source in prod PG).
- Style-level route blocked: the style has `sty_is_locked = 'Y'`; the `ELSE` branch of
  `update_stylecolorchannelattributes_ccrangecode()` reverts the style change.
- Channel-level route blocked: `sizerangecode_validsizes_members()` step `s1` does an
  INNER JOIN of `eve_l_dependencylookup` (`lookup_id='size_range'`) to
  `s5_eve_sizerange_master`. `Waist-US-Petite` was absent from both in PROD
  (only `Waist-US-24-32` and `Waist-US-Extended`), so `s1` returns 0 rows.
- **What a premature manual `UPDATE ccrangecode` would have done (read from the
  function, not executed):** ccrangecode updates, valid sizes stay `{}`, all 10
  `eve_ma_sizeattributes` rows flip `isvalid=0` with no replacements, and
  `eve_p_dc_adj_size.dc_useradj` is nulled (user overrides lost). Worse than before.
- Looked for a "Deploy Constant Tables" JIRA precedent for `eve_sizerange_master.csv`:
  none (git history of the file shows only a 2025-10 cleanup PR and a 2025-02 change
  tracked via Slack). Then found SUP-3729 (Petite Default Size Profiles): it already
  carried the `Waist-US-Petite` rows (size_run_id 29, `24P`-`32P`), validated in QA, not in PROD.
- **Root cause:** `Waist-US-Petite` missing from the size-range constant table
  (-> `s5_eve_sizerange_master` -> `eve_l_dependencylookup`), plus the style lock and
  bulk-reload pattern that bypass the sync trigger.
- Decision (JIRA comments 2026-07-30 / 08-03, Jatin Rana + Stephanie on Slack): wait
  for the constant-table deploy; no manual fix in PROD before it.

## Fix

- No code change under this ticket. Dependency deployed to PROD 2026-08-14/16
  (etl-evereve-batch PR #208 `SUP-4131_SUP-4362_SUP-4363`, bundled in PR #213; updates
  `constant_tables/eve_sizerange_master.csv`).
- The weekly batch of 2026-08-16 reloaded `s5_eve_sizerange_master` /
  `eve_l_dependencylookup` with the Petite rows (batch log: CSV copy + reload).
- Per the EE sizing deploy thread (Slack, Imthiaz Hussain), post-batch the stale
  `ccrangecode` values were corrected in PROD with section 6 of the staging script
  `eve_sizerange_update_05112026.sql` (dry run 1,738 items; approved by Chetan
  2026-08-17), which re-fires `trigger_sizerangecode_validsizes_members`, followed by
  a PG -> CH sync of the two tables and a bulk plan.

## Knowledge gained (techno-functional — required)

**Technical:** In EE PG, size eligibility is derived by DB triggers, not by the ETL.
`trigger_sizerangecode_validsizes_members` (on `UPDATE OF ccrangecode` of
`eve_ma_stylecolorchannelattributes`) rebuilds `eve_ma_sizeattributes` and
`cc_validsizes_*` from an inner join of `eve_l_dependencylookup` and
`s5_eve_sizerange_master`; both are wiped and reloaded every batch from
`constant_tables/eve_sizerange_master.csv`, so a new size run is a constant-table
change, never a live-DB insert. Weekly `DELETE`+`COPY` does not fire the trigger, so a
size-run change on an existing item needs an explicit post-batch `UPDATE` (see
`knowledge/db-trigger-matrix.md`).

**Functional:** A stylecolor's valid sizes (Regular 24-32 vs Petite 24P-32P) decide
which SKUs On Order, receipts and size curves can attach to. If the channel-level
range disagrees with the PIM/style range, the SKUs from the PO have no valid size row,
so On Order silently disappears in Flowsheet/allocation even though the PO exists.

## Gotchas

- Never run `UPDATE ... SET ccrangecode` for a size run that is missing from
  `eve_l_dependencylookup`: it invalidates every size and nulls `dc_useradj`.
- Which action actually healed `PIM-465531` is inferred: the session found no stylecolor-
  level migration in the deploy PRs and no trace in the weekly log, and matched the end
  state to the bulk section-6 correction in Slack. Not confirmed by the executor for this ID.
- The same on-order data is named differently per engine: `eve_p_onorder_by_po` exists in
  ClickHouse, `eve_p_onorder_by_po_tbl` in Vertica (querying the CH name in vsql errors "does not exist").
- Stephanie noted two other Petite ranges (Alpha / Numeric) already worked in PROD; only
  `Waist-US-Petite` was missing.
