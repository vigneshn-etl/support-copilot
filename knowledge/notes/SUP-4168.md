## Problem

Torrid prod: Top TY vs LY (Style Color Review, bottom-up) disagreed with Grid View and Summary View for some
stylecolors, with header totals and item values inflated. Reproducible in QA, reportedly not in Upgrade. Reporter's later research
widened it beyond AutoRollForward items; the Assortment Analysis > Receipt Filtered > Top TY vs LY Style Colors view was correct and
was named as the model to follow.

## Diagnosis path

Only the outcome is recorded (hub session transcripts do not cover this ticket; the work files are in `/Users/vigneshn/Desktop/JIRAs/SUP-4168/`:
app-log captures of a working vs a non-working product, the pivot and `.ftl` text copies).

- Reproduced in QA with the ticket's example stylecolors (JIRA comment 2026-06-30).
- Compared the working and non-working product pivot logs and the two metric includes (`assortment_metrics_ty.ftl` vs
  `assortment_metrics_ty_ly_lly.ftl`); conclusion in JIRA: "a filter condition was missing in the FTL file used by the Top TY vs LY view".
- **Root cause (observed in the diff, interpretation inferred):** the TY metrics query in `assortment_metrics_ty_ly_lly.ftl` read
  `p_assort_agg` (table `TY_BASE_SUM_SALES_METRICS`, first query of the file) without the latest-version filter `(a.product, a.updated_at) IN
  (SELECT product, max_updated_at FROM ${TENANT_ID}_ASST_PRODUCT_MAX_${SESSION_ID})` that the sibling `TY_BASE_SUM_RCPT_METRICS` query
  (line ~209), `assortment_metrics_ty.ftl:89` and `assortment_product_ty_ly_lly.ftl:199` already carry. `p_assort_agg` keeps multiple `updated_at` versions per product, so
  without the filter every version is summed (inflation). Which items have extra versions (AutoRollForward or otherwise) was not recorded.

## Fix

- `trd-configs` branch `SUP-4168-Top-TY-vs-LY-Roll-up-issue-fix`, commit `3fb54d3` (2026-06-30), 1 line added in
  `pivot/include/assortment_metrics_ty_ly_lly.ftl` (WHERE clause of the `TY_BASE_SUM_SALES_METRICS` query, new line 112):
  `AND (a.product, a.updated_at) IN (SELECT product, max_updated_at FROM ${TENANT_ID}_ASST_PRODUCT_MAX_${SESSION_ID})`.
- Include is consumed by `pivot/AssortmentFitTYLY.pivotdefn` (`<#include "assortment_metrics_ty_ly_lly.ftl" />`).
- Flow per JIRA: QA 2026-06-30 -> Client Service QA 2026-07-02 -> Ready for Client Deploy -> Client QA 2026-07-08 -> Done 2026-07-12. PR number not recorded.

## Knowledge gained (techno-functional — required)

**Technical:** In the Assortment pivots, `p_assort_agg` is versioned by `updated_at`; every metrics query must restrict to the per-product
max version via the session table `ASST_PRODUCT_MAX_<SESSION_ID>` (built in the `assortment_product_*.ftl` includes). A missing predicate in
one include silently multiplies metrics. When two views of the same data disagree, diff the shared `.ftl` includes line by line.

**Functional:** Top TY vs LY is the planner's best/worst-performers view; inflated unit sales or planned values there lead to wrong
buy/chase decisions, which is why parity with Grid and Summary views is the acceptance test.
