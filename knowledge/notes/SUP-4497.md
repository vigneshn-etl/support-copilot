## Problem

Belk planners could not make cluster/ranging changes via Mass Edit in Total View: the edit
looked accepted but never queued or applied. Same action worked from By-Cluster / Style Color
Parameters (Ranging tab). Reported against staging; fixed in QA 2026-08-18.

## Diagnosis path

Evidence came from darwin assortment-api logs for three screens
(`JIRAs/SUP-4497/*_mass_edit.txt`), not config reading alone.

- **Root cause (observed):** Total View submitted the edited row with `time=FY27_Q1` (quarter
  grain). `ModificationGroupPartitioner` found candidate property tables for `str_grade`
  (`storeattributes` - store grain; `assortment` - floorset grain in `M_Meta.conf`) but no exact match at quarter
  grain -> ERROR "Unable to find a property table to assign modification of str_grade" -> edit silently
  dropped (15/15 failures in Total View; the working screen sent a floorset id and logged "exact match"
  then `UPDATE blk_a_assortment`).
- Why a floorset id was missing (Mark Todd's explanation in commit `1e0a1fc`; session traced the
  blanking rule to `d45be9b`): the Total View pivot blanks `final_sent_floorset` for
  `floorset_seq_num > 1`, and the frontend overwrites the `floorset` property when consuming rows for mass edit.
- Ruled out: str_grade missing from the mass-edit dialog (present in `modifierTypes`);
  `massEditConfig.coordinateMap` mismatch vs working Targets view (identical statically);
  `editableByCalc`/`floorset_seq_num` gate (request still reached darwin); "Total View broken for
  all mass edits" - the "With Dept" tab is also quarter-grain but mass-edit of `cc_rcptint` succeeds because
  `stylecolorchannelattributes` has no time level in `M_Meta.conf`. So the fault is per-field, not per-screen.
- Dead end: copied the SUP-4453 `cc_merch_color_name` Slack "fix" (coordinateMap floorset). Diffing live QA
  config from OCI (`override_configuration/` prefix, not the stale base prefix) showed that fix was a
  `dataIndex` correction, so it did not transfer to `str_grade`.

## Fix

`belk-configs` PR #308 (branch `SUP-4497_massEditFloorset`, merged 2026-08-28), 3 lines in 2 files
(content matches Mark Todd's commit `1e0a1fc`, 2026-08-17):

- `pivot/LinePlanFloorset_RecOverride_Cluster_Targets_TotalView.pivotdefn` - add
  `temp_final_sent_floorset as pivot_floorset` (never blanked) and select it in the outer query.
- `uidefn/view/...Grouped_TotalView.viewdefn` - `massEditConfig.coordinateMap.time`: `floorset` -> `pivot_floorset`.

Rejected: adding a quarter-grain entry to the `assortment` AssortmentDefn (no quarter-grain plan record exists).

## Knowledge gained (techno-functional)

**Technical:** darwin's `ModificationGroupPartitioner` matches an edit to a property table by exact
{product, location, time} grain per field id; no cross-grain fallback, and failures log server-side only
(UI looks fine). Tables with no `time` level (e.g. `stylecolorchannelattributes`) match any grain;
`assortment` is floorset-only. Fix pattern for a quarter-scoped screen: carry a never-blanked
floorset column in the pivot and point `massEditConfig.coordinateMap.time` at it.
Store counts come from procedure `fetch_store_count` (Denver Pierce, JIRA).

**Functional:** Store Grade = cluster ranging, set per stylecolor per floorset (plans are per
floorset); Total View is a quarter-level rollup, so mass edit there must resolve down to the floorset.
