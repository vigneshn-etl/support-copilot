## Problem

Task from Chris McGinley: does any code update a placeholder stylecolor's name after its parent style is
created in Belk RMS? A published stylecolor got the new name, but another placeholder stylecolor of the
same style (valid case - not every colour is published) kept the old placeholder style name.

## Diagnosis path

- Triage (2026-08-24, reading `etl-belk-batch`): `pgsql/cyclic/process_item_po_updates.sql` (ITEM_CREATION status)
  sets create dates / locks / status but never writes `blk_d_product.name`. The only name cascade found is a
  Postgres trigger on `blk_ma_styleattributes.sty_vpn` (`Deployments/postgres/postgres_ap_ddls.sql`) that rewrites
  stylecolor names as `sty_vpn || '.' || cccolorid`. The weekly PG load reloads `blk_d_product` with triggers disabled, so no self-heal.
  (Inferred in session; not proven on data.)
- Confirmed by Praveen M (JIRA 2026-09-15, QA): changing a parent style's inbound name updates the style and the
  published colour but **not** the placeholder colour (before/after on test ids).
- Draft 1 (Praveen) selected placeholders using `blk_d_product_reduced`/`blk_in_prd_master` and `ccstylecolorcreatedate`
  IS NULL; Chris still found 42 mismatches in QA with his own queries. Chris's review:
  `_reduced` has no placeholders so `e.name <> b.name` is wrong; `ccstylecolorcreatedate` cannot be used as a
  placeholder filter because published placeholders get an artificial create date (sentinel `3000-01-01`).
- **Final approach (Chris):** the `_existing` tables are merged with Belk data in `vertica_weekly_transform.sql`, so after that
  merge derive each stylecolor's expected name from its (updated) parent style: `style.name || '.' || cccolorid`.

## Fix

`etl-belk-batch` PR #136 (branch `SUP_4520`, merged 2026-09-14) plus PR #141 (`SUP_4520_semicolon_prod`, merged
2026-10-02): `vsql/weekly/vertica_weekly_transform.sql`, right after the `blk_d_product_existing` MERGE, adds
`blk_fix_placeholder_stylecolor_name` (CTAS joining `blk_d_product_existing` / `blk_ma_stylecolorattributes_existing` /
`blk_h_prodstd_existing` / parent style, where levelid = stylecolor, `cccolorid` non-empty, name differs) and an `UPDATE`
of `blk_d_product_existing.name`. PR #141 added a missing `;` after that UPDATE (broke in prod).

## Knowledge gained (techno-functional)

**Technical:** In the Belk weekly Vertica transform, `*_existing` tables are the durable merged copy of
Belk inbound plus S5-only rows (placeholders); `*_reduced` holds only what Belk sent. Fix logic that must touch
S5-only rows has to run on `_existing` after the merges. A stylecolor's `name` is a stored string, not a live join to its style.

**Functional:** Placeholder stylecolors are planner-created colours that may never be published to RMS; when Belk
renames the parent style, planners expect the placeholder colour to read `<style name>.<colour id>`.
Published stylecolors keep their Belk-issued names.

## Gotchas

- SQL scripts here run in a multi-statement flow; a missing `;` caused a prod-only failure (PR #141).
- Do not use `ccstylecolorcreatedate IS NULL` as the placeholder test (published placeholders carry `3000-01-01`).
- Rename is weekly, not realtime - new placeholder names show after the next weekly batch.
