## Problem

Permanent-fix request for the 2026-08-13 TRD prod incident (see
[PROD-TRD-20260813-duplicate-mergekey-new-stylecolor-s5id-backfill](PROD-TRD-20260813-duplicate-mergekey-new-stylecolor-s5id-backfill.md),
which was cleaned up by hand). A new stylecolor goes out to Torrid, comes back
with a blank/raw-code `S5_ID`, and a day later the real UUID `S5_ID` arrives. Both
identities then live in `TRD_REF_S5_CLIENT_ID_MAPPING` and the batch fails.
Ticket reporter's own grep of `S5ProdMaster_*.dat` showed the same
`45264596_DEEPDEPTHS` stylecolor with blank `S5_ID` on 2026-08-12 and a UUID on 2026-08-13.

## Diagnosis path

- Mechanism already proven in the prior incident note; this ticket re-confirmed it in code.
- `vsql/weekly/010_products.sql:46-61` builds the mapping twice: (1) from today's
  `TRD_IN_PRD_MASTER` using `coalesce(S5_ID, MEMBER_ID)`, (2) a fallback from
  `trd_d_product_existing` filtered only by `id not in (select distinct s5_id from
  TRD_REF_S5_CLIENT_ID_MAPPING)`. The fallback excludes by `s5_id`, not `client_erp_id`, so
  yesterday's raw-code row is re-admitted next to today's UUID row.
- Fan-out: `trd_d_product` and `trd_h_prodstd` stylecolor inserts join the mapping on
  `client_erp_id` (010_products.sql ~275-297, ~381-404) -> 2 rows per id -> the
  `merge into trd_h_prodstd_existing ... on (src.id = dst.id)` in
  `vsql/daily/vertica_weekly_transform.sql:30` throws ERROR 3147.
- Ruled out (prior incident): a self-referential `coalesce` row inside the mapping table itself.
- Ticket suggested identifying the bad row by "s5_id length > 30 (UUID)". Session chose the exact
  test `id = client_erp_id` instead (only the raw-code fallback row has id equal to the client code);
  length checks are fragile.
- Cascade question (do child SKU rows with `ancestor0 = <raw code>` need deleting?): session grepped the PG
  schema dump for triggers/FK cascades on `trd_h_prodstd`/`trd_d_product` -> none. Reasoned (not run) that SKU rows
  self-heal because the MERGE matches on the SKU's own `id` and overwrites `ancestor0`.
- **Root cause:** existing-fallback insert dedupes on the changing column (`s5_id`) instead of the natural key (`client_erp_id`).

## Fix

- `etl-trd-batch` branch `SUP-4533`, commit `d43d3a1`, PR #235 (per JIRA comment 2026-08-18):
  `vsql/weekly/010_products.sql` (+61 lines after the first mapping build, before `trd_d_product`):
  1. `TRD_REF_DUP_CLIENT_ERP_IDS` = client_erp_ids with `count(*) > 1` in the mapping.
  2. `DELETE` the stale row (`id`/`product = client_erp_id`) from `trd_d_product_existing`,
     `trd_h_prodstd_existing`, `trd_ma_styleattributes_existing`, `trd_ma_stylecolorattributes_existing`,
     `trd_ma_sizeattributes_existing` (ticket named only 3 tables; session extended to style/size levels).
  3. Drop and rebuild `TRD_REF_S5_CLIENT_ID_MAPPING` with the same two inserts.
- Daily reuses this weekly script (via `bash/daily/06_master_load.sh`), so it self-heals every run.
- Deployed to production, per Jatin Rana's JIRA comment 2026-09-07.

## Knowledge gained (techno-functional — required)

**Technical:** `TRD_REF_S5_CLIENT_ID_MAPPING` is rebuilt every run from today's inbound master plus yesterday's persisted
state (`trd_d_product_existing`, reloaded into Vertica each run from a Postgres CSV: `bash/weekly/07.1_export_existing_pgsql.sh`,
`07.2_load_exported_psql.sh`, `vsql/weekly/load_existing.sql`). Any dedupe between those two sources must key on the natural key
(`client_erp_id`), never on the id that is expected to change. Vertica `INSERT ... VALUES` takes one row per statement (multi-row
form gave ERROR 4856) - relevant when writing QA test scripts.

**Functional:** Torrid's `S5_ID` can arrive blank for a day or more after a stylecolor is created and is filled in later; our
pipeline treated "pre-assignment" and "post-assignment" as two different products until they collided in the merge.
