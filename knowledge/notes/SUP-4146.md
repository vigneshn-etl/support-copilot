## Problem

Two stylecolors of an EE jacket style (`26122G896-BN:CHOCOLATE`, `:OLIVE`; parent ids
`0fb0a01b-...`, `e78c3383-...`) showed on-order of 10,000 instead of 5,000 for
2026_W27, and the doubling rippled through final receipt and plan quantity. High
priority: the team had to allocate the POs from these numbers (reporter Stephanie
McDaniel, prod). Acceptance: one valid SKU/size row per source mapping, correct OO,
same on `d_product` and `ma_sizeattributes`.

## Diagnosis path

From the owner's working notes ("Understanding of SUP-4146") and the ticket SQL:

- `select * from eve_ma_sizeattributes where parent_id in (<2 stylecolors>)` returned
  20 rows for 10 sizes: **2 S5 UUIDs attached to the same stylecolor + size combination**
  (10 SKU-level `pim_id`s, each with two S5 ids, spread over 2 stylecolors).
- The duplicates were present in `eve_d_product`, `eve_ma_sizeattributes`,
  `eve_h_prodstd` and `eve_p_dc_adj_size`; both on-order copies flowed into the on-order
  tables (`eve_p_onorder`, `_agg`, `_by_po`, `_by_po_tbl`, `_tbl`) in ClickHouse, which is
  why OO and the plan doubled.
- Two record sets existed per SKU: created 2026-02-16 and 2026-05-27; the 05-27 set had
  `record_state = 0`.
- Notes record that the client sends a **different SKU_ID for the same stylecolor/size
  combination** (`eve_in_prd_hier`, `eve_in_prd_attrsku`) and that stale rows also sit in the
  `_existing` tables. The note's "Find the Root Cause" section is left blank, so why the client
  re-issued SKU ids is not established.
- Checked whether `eve_p_dc_adj_size` (planner adjustments) is overwritten by the cleanup:
  yes, there are user values on both sets, so the delete is not harmless (see Gotchas).
- Chosen duplicate to keep: compared sales for the two candidate sets and kept the one with
  the max sum of sales (per the notes).

## Knowledge gained (techno-functional — required)

**Technical:** In EE the S5 id of a SKU lives in several PG tables keyed by `product`/`id`
(`eve_d_product`, `eve_h_prodstd`, `eve_ma_sizeattributes`, `eve_p_dc_adj_size`); a
duplicated stylecolor+size pair means two S5 ids, and every downstream join (on-order by
SKU, allocation) counts both. Cleanup must delete the same id set from all four tables,
back them up first, and be done before the daily so the CH serving tables rebuild clean.

**Functional:** On-order per size drives the receipt and size curve a planner allocates
from. A duplicated SKU doubles every size-level quantity for the style, so the allocation
team would over-allocate POs. Always sanity-check size rows per stylecolor (one row per
size) when OO looks exactly 2x.

## Gotchas

- Upstream cause is unresolved here: the client appears to send a new SKU_ID for an
  existing stylecolor/size. Expect recurrence; the diagnostic is
  `select parent_id, sizeattribute, count(*) from eve_ma_sizeattributes where isvalid=1 group by 1,2 having count(*)>1`
  (suggested by the symptom, not run in the recorded evidence).
- Deleting `eve_p_dc_adj_size` rows drops planner adjustments (`dc_useradj`, `dc_onorder`,
  etc.) on the removed ids; keep the one with the planner edits/sales when choosing the survivor.
- The shell showed `WARNING: there is no transaction in progress` on `commit;` — psql was in
  autocommit, so each DELETE was already committed.
- Related: SUP-4230 (OO missing for SKUs, ref mapping angle) and SUP-4364 (EE size-attribute
  sync); the prod-trigger context is in `knowledge/db-trigger-matrix.md`.
