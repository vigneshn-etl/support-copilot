## Problem

Torrid QA was restored from a backup that dropped the recently added Orig Retail text attribute (the ticket calls it
`cc_orig_retail_char`; the real column built in [SUP-4311](SUP-4311.md) is `cc_orig_unit_retail_char` - inferred, the session's
`information_schema` search for `%orig_retail%` found nothing, which is also what `cc_orig_unit_retail_char` would not match). Vignesh re-added and
populated the column in the Vertica, PostgreSQL and ClickHouse tables (JIRA 2026-07-27). QA then reported that running allocation on a worklist failed with the
`channel` NULL toaster.

## Diagnosis path

Reload step: how the column was added/populated is not recorded in any session (JIRA comment only). The allocation failure was diagnosed in a hub session
(2026-07-28/29) from QA app logs (`trd_alloc_error` capture), live-config diffs and CH queries by the human:

- First hypothesis (data gap in the channel-attribute source after the restore, by analogy to the BD note [SUP-TBD-bd-mfpapsync-lock-race](SUP-TBD-bd-mfpapsync-lock-race.md))
  -> **overturned** by the log: two separate runs in one session.
- Run 1 (real worklist item) failed in the post-pivot Python plugin: `Code: 50 ... The type "Array" of a column "Sizes" is not supported for conversion into a Arrow
  data format` (ArrowBlockOutputFormat, CH 21.4). Source: `groupArray(size_id) as Sizes` in `for_python_available_supply_tbl_${SESSION_ID}`
  (`pivot/RunAllocationPlanning.pivotdefn` ~11835), handed to `MANIFOLD PYTHON "alloc_opt"`.
- Run 2 (the visible toaster) was a retry with `arr_worklist=[]`: `CHUNK_WORKLIST` built from `worklist_id in ('')` -> empty temp tables -> `size_loc_time_master`
  scalar subquery returns NULL -> insert into non-nullable `channel` fails (Code 70).
- Why the retry had an empty worklist: `AllocationGetChunks.pivotdefn` `RE_RUN_EVAL` (lines ~147-161) only keeps worklists whose inputs changed after `last_run`.
  Suspected a NULL-bridge bug in that join; the human's CH query showed every `input_last_updated` earlier than `last_run` and `last_run` (2026-07-28 15:03:56) 11 s
  before the retry -> the gate works as designed. The first run had actually written results before the plugin crashed, so retries are "nothing to re-run".
- Ruled out: config drift for these sections (git vs QA live byte-identical), empty `s5_alloc_worklist_details_with_holdback_transfers_v2` (7 rows existed), PG
  triggers (alloc-sync triggers disabled and do not reference `channel`).
- Staging log of the same function was clean (non-empty `arr_worklist`, no Arrow error). Diffing staging live config (`trd-trd-1-staging-config`, region us-ashburn-1) against
  QA live (`internal-qa-config`, `trd/asst/override_configuration/pivot/RunAllocationPlanning.pivotdefn:11765`) found one functional difference:
  QA `MANIFOLD PYTHON "alloc_opt" PARAMS(debug=1, input_memory_limit_mb=4096)` vs git and staging `PARAMS(debug=1)`.
- **Root cause (as concluded in session; the Arrow-path mechanism is inferred):** a QA-only manual override `input_memory_limit_mb=4096` present in neither git nor staging.

## Fix

- Proposed in session: delete `, input_memory_limit_mb=4096` from the QA override object so it matches git/staging (an edit in the OCI bucket, not a PR). Optional defence-in-depth:
  guard empty `arr_worklist` in `AllocationGetChunks`/`RunAllocationPlanning` so it shows "nothing to allocate" instead of a raw CH exception (not implemented in the recorded work).
- Not recorded: who applied the change, whether it was exactly this override removal. JIRA 2026-07-30: "The below mentioned issue has been fixed in the Torrid QA environment."

## Knowledge gained (techno-functional — required)

**Technical:** In TRD allocation, "Run Allocation" = `AllocationGetChunks` (re-run gate: only worklists whose inputs changed since `last_run` in
`s5_alloc_worklist_details_with_holdback_transfers_v2`) -> `RunAllocationPlanning` (session Memory tables, then Python `alloc_opt` plugin over Arrow). If the post-pivot plugin fails *after* results
are written, retries evaluate as "up to date" -> empty `arr_worklist` -> a misleading `channel` NULL toaster. `RunAllocationPlanning` has no empty-worklist guard. The
`for_python_*` tables are session-scoped `ENGINE=Memory` (dropped by `TableCleanTask` ~60 min), so the `Sizes` array cannot be inspected after the fact.

**Functional:** After a QA restore, planners cannot allocate worklist items until the allocation stack (config overrides + attribute columns) matches the other environments; the toaster hides
which of those is wrong.

## Gotchas

- QA live OCI config can carry manual overrides that exist nowhere in git; diff live vs git AND vs the sibling environment (staging bucket is `trd-trd-1-staging-config`, not `internal-staging-config`).
- Do not read a raw `Cannot convert NULL to a non-nullable type ... channel` toaster as a data-completeness problem before checking whether `arr_worklist` was empty.
- The session could not confirm the column reload in PG (name mismatch above) or query Vertica QA (credentials failed); CH access was via the human running queries.
