## Problem

AEO's new (hindsighting) data set had to be loaded once into the staging
environment: product master, hierarchy, attributes, locations, time attributes
and the historical actuals (sales/inventory), after which the normal weekly
batch could run unattended. The JIRA has no description; scope comes from the
working document `AEO_Full_data_process_polished.docx` and logs in
`JIRAs/SUP-4183/`. This is a runbook-type ticket, not a
code defect.

## Diagnosis path

What went wrong while running the batch (from the doc's "issues" section and
logs):

- Python issue when the batch ran in tmux; the doc's fix is to create a venv in
  the brand folder and install requirements from the config dir (and commit a
  `.gitignore` entry for `.venv/`).
- `AEO_INTERFACE_MASTER` had no seed rows, so the zero-count / threshold
  checks had nothing to compare; the doc inserts one row per inbound interface
  (type IN, WEEKLY, `CHECK_ZERO_COUNT='Y'`).
- Reject visibility (inferred motive: the failure email lacked detail): the doc
  adds a `get_reject_summary_weekly` function and template change so the email
  lists FILENAME / REJECT_REASON / REJECT_FILE, plus a "Current Count is ZERO"
  check and a missing-super-class DIVISION validation in
  `001_check_inbound_rejects.sql`.
- The doc appends `/${CLIENT}` to the GCS reject path (05_export_rejects.sh,
  weekly.sh) and fixes the brand name in the mail subject (TSN `MailClient.py`),
  i.e. per-brand reject folders and subjects.
- After the run: JIRA comment 2026-06-26 reports rejects in the **Time
  Attributes** file; customer was told and corrected data awaited. Which rows
  or reasons: not recorded in the artifacts.
- For AER the `_existing` Vertica tables were emptied before reload; a single
  `TRUNCATE TABLE a, b, c` gave a Vertica syntax error, so each table was
  truncated separately (AER_Vertica_existing_truncate.txt).

## Fix

No single PR is evidenced for this ticket. Actions recorded in the doc and logs
(operator steps on the staging processor, 2026-06-22 to 06-26):

- Copied the 24 one-time files (about 243 GiB) from the production "onetime"
  GCS path to the staging inbound folder for that day, then wrote the two
  `S5RDYFile_*` ready markers so the batch picks them up.

## Knowledge gained (techno-functional — required)

**Technical:** a brand's one-time history load = stage files under the day's
inbound folder + RDY markers, pre-create/ load the CH pre-delta actuals table
by hand, seed `AEO_INTERFACE_MASTER`, then let `weekly.sh` run the
validate/reject/export stages in tmux. Reject visibility (summary email, Slack
summary, per-brand GCS reject folder) is worth wiring before the first run, not
after. Related column changes: [SUP-4182](SUP-4182.md).

**Functional:** the history load gives hindsighting its past weeks of sales and
inventory by location and price status (FP full price / MD markdown); until the
master files validate, actuals for unknown SKUs or locations are rejected, so
planners would see gaps.
