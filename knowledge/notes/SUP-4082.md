## Problem

Reported from Belk QA as a bug (Flow Type toggle returns an empty grid in the
TY/LY Grid View, and in Store Clustering > Review Clusters). Nicole Rockwell
(2026-07-17) re-scoped it to a task: Flow Status does not exist in Store
Clustering, and for TY/LY Grid it is not meaningful because the view compares
TY and LY and an item is unlikely to have the same flow status in both -
**remove the Flow Status filter from the TY/LY Grid View (Top Down and Bottom
Up, Quick and Detail tabs)**.

## Diagnosis path

- Routed as config (`belk-configs`, branch `assortment-planning`), not frontend:
  the toggle is driven by a `showFlowStatus` flag.
- Pulled live QA config from OCI (both Belk tenants `belk` and `belkap`) and
  diffed with the repo (observed): `AssortmentUiConf.confdefn` already had
  `"showFlowStatus": false` on the `TYLYGridViewWorklist` / `TYLYGridView`
  entries, yet the QA symptom report stood. That made "already fixed" look
  true when it was not - the confdefn flag was not what controls the Quick /
  Detail tabs (inferred, see Fix).
- Worry "does the flag even work?" checked in the shared frontend
  (`assortmentui`): `Worklist.container.ts` / `Worklist.tsx` gate the toolbar
  toggle on `showFlowStatus`; `GridView.selectors.ts` passes it as
  `shouldFilterFlowStatus`; `ListGridPair.selectors.ts` (~line 221) forces the
  filter array to empty when false. TRD/EVEREVE/EXPRESS configs use the same
  flag in production.
- Ruled out a version-lag theory using `deployment-configs`: Belk QA is two
  envs (`belk`: UI `dev`, backend release; `belkap`: UI `main`) and the flow
  status code is identical on both branches, filtered client-side only.
- **Cause of the empty grid** (Nicole's functional explanation; the session's
  guess that the transpose pivot cannot filter by flow status is unverified):
  a TY/LY comparison has no single flow status per row.

## Fix

`belk-configs` PR #304 (commit `9f93d87`, Mohit Tiwari, merged 2026-08-06 into
`assortment-planning`): add `"showFlowStatus": false` to each tab's
`componentProps` in

- `uidefn/view/HistoryStyleColorTYLYGridWorklist.viewdefn` (Bottom Up, Quick
  and Detail tabs)
- `uidefn/view/TD_HistoryStyleColorTYLYGridWorklist.viewdefn` (Top Down, Quick
  and Detail tabs)

The first attempt (2026-08-05) removed it only from Bottom Up; QA (sudeep.singh)
still saw it in Top Down, so the TD viewdefn was fixed the same day.

## Verification

sudeep.singh (QA, 2026-08-05) confirmed the Flow Status filter is gone in the
TY/LY Grid View in both Top Down and Bottom Up, Quick and Detail tabs (POT
attached to the ticket). Then Client Service QA (08-17), Ready for Client
Deploy (08-31), Client QA, Done (10-05).

## Knowledge gained (techno-functional - required)

**Technical:** A grid tab's `showFlowStatus` is controlled by the `componentProps`
of that tab in the `.viewdefn` (per-tab); changing the global/other-entry flag
in `AssortmentUiConf.confdefn` is not sufficient (inferred from the fix that
shipped). Top Down views are separate `TD_*` viewdefn files and must be
changed in lockstep with the Bottom Up ones. The flow-status filter is applied
client-side; it is not an API parameter.

**Functional:** Flow Status (New / Carryover / Living On Floor) classifies an item
in one period. It is meaningful in single-period grids but not in TY/LY
comparison grids, where the item may have a different status in each year.
