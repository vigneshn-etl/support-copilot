## Problem

At style level the UI shows one stylecolor image, meant to be the stylecolor
with the highest sales dollars in that style. For AEO style 1164_5094 (Mens Knit
Tops, North America, FP+MD, Feb weeks) three views disagreed: NAVY (most style
views), Black (Top TY vs LY), Pink (TY/LY Grid companion). The item did not
exist last year, so LY data was not the explanation (reporter's note).

## Diagnosis path

Only the diff and QA evidence survive (no session transcript):

- (inferred) Most Style views were right (NAVY, matching the later-verified
  best seller); only the two TY/LY families
  (Top TY vs LY, TY/LY Grid) were wrong, so the fault is in the TY/LY pivot
  family, not in the shared hierarchy or the image attribute.
- **Top TY vs LY path:** `HistoryFitStyleTYLYTranspose.pivotdefn` mapped a
  style to a color with `ANY LEFT JOIN (select distinct style, stylecolor from
  TY_PRODUCT UNION ALL LY_PRODUCT) USING (style)`. That subquery has no sales
  ordering, so `ANY` returns an arbitrary stylecolor of the style. (inferred
  from the removed code; the commit replaces it with a sales-ranked pick)
- **TY/LY Grid path:** in `include/history_metrics_style_ty_ly_lly.ftl` the
  `STYLE_TEMP` / `LY_` / `LLY_` tables computed `sum(net_sls_r)` by joining
  the all-base table on `a.product = b.style`, grouped by stylecolor. Then
  `STYLE_MAPPING` keeps `ORDER BY style, slsr_x desc LIMIT 1 by style,
  s5flowstatus`. (inferred) If the summed measure is at style level the same
  value repeats on every stylecolor and the "top" one is arbitrary.
- **Root cause (inferred from the fix, not stated in JIRA):** the best-color
  ranking was not computed from stylecolor-level `net_sls_r` over the selected
  time window, so the winner was not the real top seller.

## Fix

`s5-stratos/aeo-configs` PR #12 (branch `SUP-4193-fix-image-selection`,
commits `dfbc885` 2026-06-19 and `d4b8c42` 2026-06-20, merged 2026-06-22 into
`hindsighting`):

- `pivot/include/history_metrics_style_ty_ly_lly.ftl` — new session tables
  `SC_SALES_RANK`, `LY_SC_SALES_RANK`, `LLY_SC_SALES_RANK`: per stylecolor
  `sum(net_sls_r)` from `p_history_agg`, restricted to the session's TY/LY/LLY
  products and the matching `ty/ly/lly_week_id` weeks. `STYLE_TEMP` (and LY/LLY)
  now `INNER JOIN` those rank tables instead of re-summing.
- `pivot/HistoryFitStyleTYLYTranspose.pivotdefn` — the style-to-color join now
  ranks stylecolors by `sum(net_sls_r)` over TY and LY products and weeks and
  keeps `LIMIT 1 BY style`. Second commit swaps the hierarchy source to
  `${TENANT_ID}_stylecolor_hier_attr` and adds the week restriction.
- Which file feeds which UI view (TYLY vs Transpose models) was not confirmed
  here; both Top TY vs LY and TY/LY Grid View are covered per JIRA.

## Knowledge gained (techno-functional — required)

**Technical:** `ANY LEFT JOIN ... USING (style)` and `LIMIT 1 BY style` are only
as deterministic as the ORDER BY feeding them; any "representative color"
lookup must rank at stylecolor grain with the same time filter as the view.
Each pivot family builds its own `STYLE_MAPPING`, so a fix in one family does
not carry to the others (TY/LY and its Transpose variant are separate code).
`HistoryFitStyleTYLY*` share `history_metrics_style_ty_ly_lly.ftl`.

**Functional:** the style tile image is a merchandising signal ("this is what
the style looks like when it sells"); it must be the best-selling color by net
sales $ in the selected weeks, and must be the same wherever the style appears.

## Gotchas

- The best color depends on scope: weeks, location, price status. Compare views
  using the same scope before calling a mismatch a bug.
- AEO config fixes should be replicated to the UNS/TSN/AER config repos; not
  verified here whether that was done for this ticket.
